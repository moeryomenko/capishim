# Using capishim

After [install.md](install.md) completes, the management apiserver is
reachable through the admin kubeconfig at `~/.kube/capishim.kubeconfig` (a
symlink to `${CAPISHIM_STATE_DIR}/kubeconfigs/admin.kubeconfig`, written by
the setup container at boot). All commands below use
`KUBECONFIG=~/.kube/capishim.kubeconfig`.

## Accessing the management cluster

```sh
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get clusters
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get clusterclass
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get crd
```

`kubectl get clusters` returns the Cluster API resources in the default
namespace (none before the first provisioning run). `kubectl get clusterclass`
proves the topology gate is active — every manager runs with
`--feature-gates=ClusterTopology=true`. `kubectl get crd` lists all Cluster
API CRDs installed by the setup container (Cluster, Machine,
MachineDeployment, MachineSet, MachineHealthCheck, ClusterClass,
ClusterResourceSet, KubeadmConfig, KubeadmConfigTemplate,
KubeadmControlPlane, DevCluster, DevMachine, DevClusterTemplate,
DevMachineTemplate, DevMachinePoolTemplate).

## Provisioning an in-memory workload cluster

The in-memory templates are vendored from upstream cluster-api and copied into
the state directory by `make install-quadlet` (`${CAPISHIM_STATE_DIR}/templates/`,
default `~/.local/share/capishim/templates/`). Create a ClusterClass-based
cluster:

```sh
KUBECONFIG=~/.kube/capishim.kubeconfig clusterctl generate cluster <name> --from ~/.local/share/capishim/templates/cluster-template-in-memory.yaml --kubernetes-version v1.36.1 --control-plane-machine-count 3 --worker-machine-count 3 | KUBECONFIG=~/.kube/capishim.kubeconfig kubectl apply -f -
```

Replace `<name>` with the cluster name (also the `CLUSTER_NAME` template
variable). The command renders the template, substituting
`KUBERNETES_VERSION`, `CONTROL_PLANE_MACHINE_COUNT`, and
`WORKER_MACHINE_COUNT`, and applies the Cluster object in the target namespace
(default from the kubeconfig context).

The Cluster's `topology.classRef` points at the `in-memory` ClusterClass, which
is a separate object: it is not generated by the cluster template. Apply it
first from the vendored `clusterclass-in-memory.yaml` (this creates the
DevClusterTemplate, KubeadmControlPlaneTemplate, DevMachineTemplate,
KubeadmConfigTemplate, and ClusterClass objects — the e2e suite uses the same
order, ClusterClass then cluster template):

```sh
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl apply -f ~/.local/share/capishim/templates/clusterclass-in-memory.yaml
```

The ClusterClass objects carry no namespace and land in the kubeconfig context
namespace (default: `default`), which must match the namespace the cluster
template renders into.

Watch provisioning progress:

```sh
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get cluster <name>
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get kubeadmcontrolplane
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get machine
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl get secret <name>-kubeconfig
```

The full CAPI state machine completes: `Cluster.status.phase` reaches
`Provisioned`, the KubeadmControlPlane reports `Initialized=true`/`Ready=true`
with the desired replicas, all Machines report `Ready`, and the
`<name>-kubeconfig` Secret exists. The Secret is the workload cluster's
kubeconfig for the in-memory apiserver. The in-memory cluster has no real
kubelet, so it cannot run real workloads — it exists to exercise the CAPI
reconciliation contract.

## Scaling

The cluster is ClusterClass-based: the topology controller owns the
KubeadmControlPlane and MachineDeployment objects, so scale by patching the
Cluster topology, not by `kubectl scale` on the generated objects. The
KubeadmControlPlane webhook also forbids even control-plane replica counts
with stacked etcd, so control-plane targets must be odd:

```sh
KUBECONFIG=~/.kube/capishim.kubeconfig kubectl patch cluster <name> --type=json -p '[
  {"op":"replace","path":"/spec/topology/controlPlane/replicas","value":5},
  {"op":"replace","path":"/spec/topology/workers/machineDeployments/0/replicas","value":5}
]'
```

The template produces exactly one worker MachineDeployment (`md-0`, the
`default-worker` class), so index `0` in the JSON patch is the worker
deployment. The topology controller reconciles the KubeadmControlPlane and
the MachineDeployment to the new counts.

## Restart and reboot semantics

The pod can be restarted at any time:

```sh
systemctl --user restart capishim-pod
```

State persists across restarts and host reboots because it lives on the host
volume, not in container filesystems:

- `${CAPISHIM_STATE_DIR}/etcd/` — etcd data;
- `${CAPISHIM_STATE_DIR}/pki/` — pod CA, component certs, SA signing keys;
- `${CAPISHIM_STATE_DIR}/kubeconfigs/` — manager and admin kubeconfigs.

Cert generation is idempotent: if the CA already exists, the pki container
does not regenerate it, so previously issued kubeconfigs keep
authenticating. After `systemctl --user restart capishim-pod`:

- existing clusters remain `Provisioned` and keep reconciling;
- the pre-restart admin kubeconfig still works.

For reboot persistence in the user scope, lingering must be enabled. The
install step enables it automatically (best-effort); verify with:

```sh
loginctl show-user "$(id -u)" -p Linger
```

If the stack does not come back after logout/login or reboot, enable it
manually: `loginctl enable-linger`.

## RBAC model

There is no kube-controller-manager in the stack, so the setup container
creates the RBAC model directly:

- each provider manager is a User identity (client-cert CN,
  e.g. `capishim:core-manager`) bound to the same ClusterRoles the provider's
  stock manifests grant its ServiceAccount — the bindings point at the
  concrete `*-manager-role` roles (the aggregated role shell grants nothing
  without a controller aggregating it);
- the admin identity is bound to `cluster-admin`;
- an unbound identity receives `Forbidden` on `list clusters`.

Manager kubeconfigs live in `${CAPISHIM_STATE_DIR}/kubeconfigs/` and are
mounted read-only into the manager containers.

## Full verification flow

```sh
make verify-shim
```

runs the complete verification contract:

1. `make check` — lint + vet + unit tests (VC-09);
2. `make check-pins` — upstream pin consistency across go.mod, Containerfile
   source ref, and vendored template provenance (VC-10);
3. `make test-e2e-shim` — the ginkgo e2e suite (VC-01..VC-08) against the
   capishim pod.

The e2e suite drives podman directly (no systemd) — it creates the capishim
pod with the same component table, flags, and volumes the quadlet units
render, then asserts the full contract: quadlet bootstraps on a clean host,
setup idempotency and cert persistence, CRD + RBAC provisioned, webhooks
functional after rewrite, in-memory cluster reaches Provisioned, restart
persistence, ClusterClass + MachinePool served, and a green suite with the
shim bootstrap. Run it in the repo root; it takes roughly 10-15 minutes.

## Non-objectives (what capishim is not)

- No real workload clusters: no Docker socket, no real kubelet, no CNI. The
  fake in-memory cluster is the only workload target.
- No `clusterctl init`/`clusterctl move`: the shim performs its own init.
- No Runtime SDK / runtime extensions (`RuntimeSDK` gate stays off).
- CAPD in-memory is the only infrastructure provider.
